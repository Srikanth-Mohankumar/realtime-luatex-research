From a 20-second build to a live page:
the warm compile architecture

Every correction in the PGC Editor used to pay a full XML→TeX→PDF compile — about 20 seconds, mostly spent re-doing work that had not changed. The new architecture keeps that work resident in warm engine processes, so a build costs only what actually changed. Same templates, same output — verified byte-for-byte — just without the repeated cold starts.

Memory is bounded by process count, not hope: engine pool and workspaces are hard-capped with idle reapers, and the container now runs under an explicit mem_limit. One heavy-template article ≈ 2–3 GB resident; the light demo article ≈ 0.3 GB.

Concurrency & capacity

Scaling out is by article count, not user count: capacity planning is concurrently-active articles × 2–3 GB against the container’s memory envelope. Beyond one host, articles shard cleanly across backends because nothing warm is shared between articles — sticky-route by article id and each backend owns its warm set, with the shared file server still the only truth.

Why this is safe to roll out

Safety rails

Cold path never removed

Any warm-path failure falls back to today’s pipeline automatically. Worst case equals current behavior.

Output-identical, gated

A golden byte/text comparison between cold and warm output guards the flag per customer; engines are single-shot so no state can leak between builds.

Flag-gated rollout

WARM_ENGINES=1 per environment; Elsevier/1.x untouched until its own decision.

Observable

/metrics: per-stage warm/cold histograms per customer; the fallback-rate counter is the health canary.

Memory bounded

Engine and workspace counts hard-capped with idle reapers; container mem_limit; warm state is disposable by design.

Tested

First-ever compile-path test suite: 33 unit tests plus an end-to-end golden test runnable against any dataset.
